Privacy Policy for Attention

Last updated: 24 September 2026

Attention is a browser extension that lets you trust and rate X accounts and posts with a Nostr key stored in an encrypted vault on your device. This policy describes the data the extension handles. Attention does not run its own server and does not use analytics.

What data the extension handles

On x.com and twitter.com, Attention reads public information already on the page:

  • Numeric X account IDs, lowercase handles, and related post IDs
  • The time of that observation and which allowlisted X operation it came from
  • The signed-in account’s numeric ID, taken from the public twid cookie value (u=<id>). The raw cookie string is not stored.

A page script may inspect copies of allowlisted X responses to read those public IDs. Direct messages, protected content, authorization tokens, and other personalized fields are not forwarded or saved. When you turn on a hide or trust filter, that same page script may hide matching items in allowlisted home-timeline responses so X does not draw them. The raw response stays in the page.

To find a NIP-39 identity proof, the page may call X’s own SearchTimeline GraphQL in your signed-in session. That runs when your local identity record has no verified binding yet: when you open the Attention panel on X, or when you choose Trust on an account. Only a validated match (post ID, handle, and proof text) is kept. Cookie strings and raw GraphQL bodies stay in the page.

To check a NIP-39 claim, the extension may fetch the public profile HTML for the claimed handle, and oEmbed data from publish.twitter.com for a proof post you supply. Those requests are sent without your X credentials. After you preview a proof, confirm the active account, and approve it, Attention may open X’s compose window with the proof text and record the post ID you publish. It does not post, like, follow, delete, or message on your behalf.

On your device, Attention stores:

  • An encrypted vault of your Nostr secret key, plus public account metadata such as an optional binding to an X account ID
  • Relay URLs, NIP-07 site approvals, and small settings
  • A non-secret index of X account ID, Nostr public key, and timestamps
  • Optional Easy-account roaming blobs, which are NIP-49 ciphertext only
  • Signed Nostr events you create or sync, including kind 32009 trust statements, kind 32014 ratings, and kind 10011 identity links, plus indexes, sync cursors, X identity records, and pending relay delivery state

The identity and identity.email permissions are used only to ask Chrome whether this browser profile is signed in. Attention checks that a profile id or email is present. It does not save the email address or the profile id.

If you enable NIP-07 for a site, that site can ask Attention to sign a Nostr event. The request is shown for your approval. The secret key stays in the extension service worker and is not given to the page. Attention does not implement payments.

How data is stored

  • chrome.storage.local holds the encrypted vault, settings, and related account metadata on this browser profile.
  • chrome.storage.sync holds relay URLs, your active Nostr public key, the X-to-Nostr binding index, and optional Easy-account ciphertext so Chrome Sync can restore them on your other signed-in browsers. Chrome Sync stores that data with Google under your Google account.
  • IndexedDB in this browser profile holds events, identity records, and sync state.

How data is used

  • To show trust and ratings for X accounts and posts you are looking at
  • To remember which Nostr key is bound to which X account
  • To sign and publish statements you choose to publish
  • To sync those statements with the Nostr relays you configure
  • To verify NIP-39 proofs that link a Nostr key to an X account
  • To approve or refuse NIP-07 signing requests from sites you have enabled
  • To detect a signed-in Chrome profile so Easy-account roaming can run

Third-party services

Attention does not send this data to a server operated by Attention. Data leaves your device only in these cases:

  • Nostr relays you configure. The extension queries them for public trust statements, ratings, and identity links, and publishes events you choose to sign. Published events are public. A relay may keep them indefinitely. Each relay operator has its own practices.
  • X (x.com, twitter.com, and publish.twitter.com). Proof search uses your existing X session in the page. Proof checks use unauthenticated requests for public profile HTML and oEmbed data. X Privacy Policy.
  • Google Chrome Sync, for the chrome.storage.sync items listed above. Google Privacy Policy.

Data sharing

Attention does not sell data and does not share it with advertisers. Public Nostr events you publish can be read by anyone who queries the relays that store them. Chrome Sync data is available to Google as part of your browser sync, and to other browsers signed into the same Chrome profile.

Data retention and deletion

Local data stays in this browser profile until you remove it. Uninstalling Attention removes the extension’s local storage and IndexedDB. Data already copied by Chrome Sync remains in your Google account until you clear Chrome Sync data. Events already accepted by a relay stay on that relay until the relay deletes them; publishing a newer replacement or a delete event updates what Attention treats as current, and the relay decides what it keeps.

You can remove a local X binding, change relays, and delete or replace statements from inside Attention. Clearing the extension’s site data in Chrome removes the local vault. Export or back up a key you want to keep before you do that.

Changes to this policy

If these practices change, this page will be updated and the date above will change. The copy in the Attention source repository is the current policy.
