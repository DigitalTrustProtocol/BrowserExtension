The core of NIP-32009 is good, but it won't hold up to outside review yet. Six issues stand out. The biggest is that it never defines what "trust" means for hops, and the product already contradicts the spec on that point. The rest are slot-identity bugs, wire conventions that clash with existing NIPs, and app policy mixed into the protocol text.

## What's solid (keep it)

- **One subject per event, one addressable slot per author × subject × context.** Replacement is deterministic and easy to reason about.
- **Recomputing `d` from the tags and rejecting mismatches.** A `d` can never claim one slot while the tags describe another.
- **Separate meanings for empty and zero.** Empty `v` retracts and `0` is a real Neutral, matching `32014`'s empty-score-vs-`0` rule.
- **A ternary value plus a separate graded rating kind.** This is the right way to stop likes from posing as trust.
- **A clear line between inputs and outputs.** Statements are inputs, NIP-85 holds derived scores, and hints are explicitly untrusted.

## Serious problems

### 1. The spec never says what `v=1` means, and the product contradicts the spec on `identity`

Trust research separates two kinds of trust. One is "I trust Bob for X" (functional trust). The other is "I trust Bob's judgment about whom to trust for X" (referral trust). Only the second can safely be chained across hops (see Jøsang & Pope, *Semantic Constraints for Trust Transitivity*). The spec only says "positive `p` MAY be a traversal hop", without saying in which context or with what meaning.

The spec then defines `identity` this way:

```291:294:docs/NIP-32009.md
- `identity` — trust that the subject is who they claim to be (account /
  authenticity). This does **not** imply trust of what they write; use post
  subjects (`post:id`) or another purpose for content judgments.
```

It also recommends no `c` at all as the default when trusting an X user (line 289). The product does the opposite:

```75:78:docs/architecture.md
`user:id:<numeric-id>` and `post:id:<post-id>`. New X person-trust statements use
**`s=x.com`** and **`c=identity`**. Post kind `32009` trust and post kind `32014`
ratings omit `c`. Kind `32009` queries always use `identity` so Trust hops walk
the person-trust graph; empty post slots still resolve through identity→general
```

So "I believe this account is really NASA" ends up deciding whose ratings and whose further trust you read. The spec says that is exactly what `identity` does *not* mean. A careful reviewer will find this first.

**Fix:** add a "Semantics" section. For example: positive trust of an agent in context C means the author accepts that agent's `32009` statements in C as input. Then either walk the global context, or redefine `identity` the way PGP treats key certification ("I trust their vouching for who is real").

### 2. Mandatory fallback to global trust is a security hole

Lines 279–287 say clients MUST fall back from the exact context, through its parent prefixes, to global. `wot-questions.md` uses `c=security:access:…` to "open a door". Put together: if I trust Alice globally ("good person") and never said anything about the front door, a client is *required* to let her in. Line 821 ("Do not silently widen `c`") contradicts this, and `32014` explicitly forbids fallback.

**Fix:** fallback is the reader's policy, not wire format. Make it MAY, and say that safety-relevant contexts should not fall back.

### 3. `s` is half part of the subject and half a search tag

`s` goes into `d`, so it defines the slot. But the resolver ignores it ("Resolve uses subject + c", line 251). As a result, one author can have several *live* statements about the same X user: one with no `s`, one with `x.com`, and one with `twitter.com,x.com`. Each is a different slot, and the graph collapses them by an undocumented rule (product policy: "x.com precedes empty").

The multi-scope example (lines 617–640) is the worst case. It is presented as handling the twitter→x rename, but it actually creates a *third* slot. A platform renaming its domain is exactly the long-term scenario the format needs to survive. Related problems:

- `user:id:11348282` with no `s` means nothing; it could be any platform's user 11348282.
- Validation item 6 forces decimal ids on `user:id` everywhere, which rules out Reddit, YouTube, and others.
- In trust research, "scope" usually means purpose, which is what this spec calls `c`. Readers from that field will be confused.

**Fix:** make the namespace required and single-valued for platform-local ids. Treat it as a stable token, not a hostname, and let clients map aliases. Apply id-format rules per namespace. Rename `s` to "namespace".

### 4. The `d` material is ambiguous and has no test vectors

Line 396 claims the fixed colons prevent collisions. That only holds for *empty* fields. `i` values and `c` both contain colons, and the code doesn't forbid `:` or `,` in `s` (`isCanonicalTrustScope` only checks non-empty, the length limit, and lowercase). Two collisions that both pass validation:

- `i=web:https://e.com/p`, `s=x.com`, `c=a:b` and `i=web:https://e.com/p:x.com`, `s=a`, `c=b` produce the same material, so they share one slot.
- `s=["a,b"]` and `s=["a","b"]` produce the same scope string.

"Sorted lexicographically" is also undefined. JavaScript's `.sort()` compares UTF-16 code units, which differs from byte order for some non-ASCII values. All the examples use `<sha256(...)>` placeholders, so independent implementations have nothing to check against.

**Fix:** hash a JSON array, the same idea NIP-01 uses for event ids, e.g. `sha256(JSON.stringify(["i", subject, namespace, context]))`. Restrict namespace to ASCII and publish real hex test vectors.

### 5. It reuses tag positions and letters that other NIPs already own

- **Subject tag positions:** `p[2]` is a relay hint (NIP-01), `e[2]` is a relay hint (NIP-10), and `i[2]` is a URL hint (NIP-73, which this spec cites as its inspiration). The spec puts `user:name:…` and npubs there.
- **Bech32 in tags:** a bare `npub1…` inside a tag goes against NIP-19, which says bech32 is for display, not events.
- **`l` labels:** in NIP-32, `["l", label, namespace]` has the namespace mark in position 2. Here position 2 holds free text, so NIP-32 clients will read the description as a namespace.
- **`x` and `y` for time:** `x` is the file hash in NIP-94 and Blossom, and NIP-40 already defines `expiration`. Either reuse NIP-40 or use multi-letter tags, and explain why.
- **Nostr subjects as `i`:** the code accepts `i=nostr:pubkey:<hex>` and `nostr:profile:<hex>` alongside `p`, which gives three slots for one pubkey. It also uses `nostr:addr:` instead of an `a` tag. Allow one canonical form: `p`, `e`, or `a`.

**Fix:** move identity hints into their own tag with hex values, or drop them. Attaching an identity claim to a trust statement is arguably a third question that deserves its own event.

### 6. The spec says `i` is terminal, but the product walks bound X users as hops

Line 230 and line 795 say `i` subjects are terminal. The product's whole model ("Trust UI for people and issuers (`p`, X `user:id`)") rebinds a verified `user:id` to its npub and walks it as a hop. Other implementers reading the spec will build a different graph from the same events.

**Fix:** define agent subjects versus artifact subjects. State that an account `i` becomes traversable only after the reader has independently verified a key binding, and never from a hint alone.

## Smaller cleanups

- **Remove product policy from the NIP.** "Attention product policy", the `xIdentities` table, the ~144-character cap, "Subscribe all", "winning", "hitting degree" (never defined), and the local question UI belong in `architecture.md`. A NIP describes the protocol, not one app.
- **Parsing `i` needs `k`.** `user:id:…` has three parts while `hash:<hex>` and `web:<url>` have two, so `i` can't be split without `k`. Either require `k` or close the list of classes.
- **Move legacy notes to a changelog.** "Earlier drafts used `v=0` as cancel" quietly turns old cancels into Neutrals that block fallback.
- **Explain the side effect of future activation.** A statement with a future `x` immediately switches off the current statement in that slot.
- **Define how kind-5 (NIP-09) deletions interact with the empty-`v` tombstone.**
- **Add a "Why not existing NIPs" section** covering NIP-32 labels, NIP-56 reports, NIP-51 lists, and NIP-85.
- **Add a privacy section.** Public `-1` statements carry defamation and harassment risk, and people will eventually want private statements encrypted like NIP-51 lists.
- **Cut the repetition.** The Delete rule appears about five times, which invites drift. Specify "Unicode characters" as code points.

## Direct answer to "is anything stupid?"

Yes, four things:

- The `twitter.com,x.com` example.
- Putting `s` into `d` while the resolver ignores it.
- MUST-fallback-to-global next to a front-door access example.
- `identity` defined as "not trust in what they write" while it is the edge that decides whose writing you read.

Everything else is fixable polish.
