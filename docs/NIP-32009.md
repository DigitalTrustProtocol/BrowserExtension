# NIP-32009

## Single-Subject Digital Trust Statement

`draft` `optional`

## Status

This document is an experimental proposal for event kind `32009`. The kind was
not listed in the commonly used Nostr kind registries when this draft was
written. Implementers should coordinate registration before treating it as a
stable interoperable standard.

## Abstract

Kind `32009` records one author's explicit trust, cancellation, or distrust of
exactly one subject.

The event is addressable because its kind is in the `30000`–`39999` range. For
each author, subject, and context, a newer event replaces the older event by
using the same `d` tag.

The event stores a direct trust input. It does not store an objective truth
value or a final reputation score. Clients and services calculate reputation
from selected trust statements according to their own roots and policies.

## Motivation

Social signals such as follows, likes, reposts, and engagement counts do not
necessarily express trust. A user may follow an account for entertainment,
research, or monitoring while distrusting it as a source of security,
financial, or factual information.

Kind `32009` provides a small, explicit, directional trust primitive:

- `1` means trust.
- `0` cancels the previous statement.
- `-1` means distrust.

Trust can be scoped to a context such as `development`, `news:accuracy`, or
`commerce:p2p`.

### Why exactly one subject?

An event containing multiple subjects creates difficult replacement semantics.
Changing or cancelling one subject can require republishing the entire batch,
and concurrent updates can unintentionally restore or remove unrelated
statements.

Kind `32009` therefore requires exactly one subject. This gives every
`(author, subject, context)` tuple its own addressable slot and makes:

- replacement deterministic;
- cancellation independent;
- relay queries simpler;
- local indexes smaller and easier to validate;
- synchronization and conflict resolution predictable.

Clients MUST reject kind `32009` events with zero or more than one subject.

## Relationship to other Nostr events

### Kind `3`

A follow list expresses social attention. Clients MUST NOT infer that following
someone is equivalent to trusting them.

### NIP-32 labels

NIP-32 kind `1985` labels are suitable for flexible classification. Kind
`32009` is narrower: it defines a replaceable, ternary, single-subject trust
statement intended for directed trust graphs.

### NIP-85 trusted assertions

NIP-85 can publish derived assertions such as rank or reputation outputs. Kind
`32009` instead publishes direct graph inputs. A client may calculate a score
from kind `32009` statements and publish the resulting assertion through
NIP-85.

### Kind `32010`

The draft kind `32010` trust proposal permits multiple subjects in one event.
Kind `32009` deliberately removes batching and requires one subject per event.

## Specification

### Event kind

```text
kind: 32009
```

Kind `32009` is an addressable event. Its address is determined by:

```text
32009:<event-author-pubkey>:<d-tag>
```

### Content

`content` is optional human-readable context for the statement, such as:

```text
Audited two releases from this maintainer.
```

Content SHOULD NOT exceed 1024 Unicode characters. Long evidence SHOULD be
published as another Nostr event or external resource and referenced from the
content.

Applications MUST NOT interpret content as structured protocol data.

### Required tags

A valid event contains:

- exactly one `d` tag;
- exactly one subject tag: one `p`, `e`, or `i` tag;
- exactly one `v` tag.

The following tags are defined:

- `["d", "<statement-id>"]` — required addressable identifier.
- `["p", "<pubkey>"]` — subject is one Nostr public key.
- `["e", "<event-id>"]` — subject is one Nostr event.
- `["i", "<typed-subject-id>"]` — subject is one non-`p` identifier.
- `["v", "<value>"]` — required trust value: `"1"`, `"0"`, or `"-1"`.
- `["c", "<context>"]` — optional trust context.
- `["x", "<unix-seconds>"]` — optional activation time.
- `["y", "<unix-seconds>"]` — optional expiration time.

There MUST be exactly one subject across all `p`, `e`, and `i` tags. Any event
containing more than one of these tags, including two tags of the same type, is
invalid.

### `p` subject

Use `p` when the subject is a Nostr identity:

```json
["p", "<64 lowercase hexadecimal public key>"]
```

The value MUST be exactly 64 lowercase hexadecimal characters.

A positive `p` statement can be used as a directed edge when expanding a local
trust graph.

### `e` subject

Use `e` when the subject is a Nostr event:

```json
["e", "<64 lowercase hexadecimal event ID>"]
```

The value MUST be exactly 64 lowercase hexadecimal characters. A `note1`
identifier MUST be decoded to its event ID before it is placed in the `e` tag.

An `e` statement is a terminal trust subject and is not a graph-expansion edge.

### `i` subject

Use `i` for subjects that are not represented directly by a Nostr public key or
event:

```json
["i", "<typed-subject-id>"]
```

Recommended forms include:

- `nostr:profile:<normalized-profile-reference>`
- `nostr:addr:<normalized-address-reference>`
- `nostr:pubkey:<normalized-pubkey-reference>`
- `hash:<64-lowercase-hex-sha256>`
- `web:<normalized-absolute-url>`
- `ext:<normalized-external-id>`

The type prefix is part of the subject identity. For example,
`web:https://example.com/alice` and `ext:example:alice` are different
subjects.

`nostr:pubkey:` identifies a pubkey as a scored subject, but it is not a graph
expansion edge. Use a `p` tag when the statement should participate directly in
trust-path traversal.

### Subject normalization

Publishers MUST normalize the subject before constructing the event and `d`
tag. Readers MUST use the subject exactly as encoded when verifying `d`.

At minimum:

- Nostr hexadecimal identifiers are lowercase.
- An `e` subject is the decoded 64-character lowercase event ID, not a
  `note1` or `nevent1` encoding.
- NIP-19 identifiers are decoded to their canonical underlying identifier when
  a canonical hexadecimal or address representation exists.
- A `hash:` value contains exactly 64 lowercase hexadecimal characters.
- A `web:` value is an absolute `http` or `https` URL with a lowercase scheme
  and host, no fragment, and no default port.
- An `ext:` value follows the normalization rules of its external identifier
  namespace.

Applications defining additional normalization MUST document it. They SHOULD
avoid changing semantically significant URL paths or query parameters.

### Trust value

The `v` tag MUST contain one of:

- `"1"` — trust;
- `"0"` — cancel or revoke the previous statement;
- `"-1"` — distrust.

`v = "0"` means that the resolved slot has no active trust edge. It does not
mean neutral evidence or a trust score of zero.

Publishing `v = "0"` without an earlier statement is valid but has no graph
effect.

### Context

The optional `c` tag scopes the statement:

```json
["c", "security:audit"]
```

A missing `c` tag or an empty context means general trust.

Contexts MAY use colon-separated levels, from broad to specific:

- `development`
- `security:audit`
- `news:accuracy`
- `commerce:p2p`
- `incident:active`

When resolving a requested context, clients SHOULD:

1. use an exact context statement when present;
2. otherwise use the nearest parent context;
3. otherwise use the general statement;
4. otherwise resolve to no statement.

For example, `security:audit:web` can fall back to `security:audit`, then
`security`, then the general context.

## Building the `d` tag

The `d` tag is deterministic for the subject and context.

### Step 1: Build the normalized subject string

- For a `p` subject, use the 64-character lowercase public key.
- For an `e` subject, use the 64-character lowercase event ID.
- For an `i` subject, use the complete normalized typed identifier, including
  its prefix.

### Step 2: Build the subject ID

If the normalized subject string is exactly 64 lowercase hexadecimal
characters, use it directly.

Otherwise:

1. encode the normalized subject string as UTF-8;
2. calculate SHA-256;
3. encode the 32-byte result as 64 lowercase hexadecimal characters.

This value is `subject_id`.

### Step 3: Add context

For a missing or empty context:

```text
d = <subject_id>
```

For a non-empty context:

```text
d = <subject_id>:<context>
```

The first 64 characters are the subject ID. A colon separates the subject ID
from the context. The context suffix MUST exactly match the `c` tag.

### Verification

Clients MUST recalculate `d` from the event's subject and context. If the
calculated value differs from the published `d`, the event is invalid.

## Replacement and cancellation

For one author, subject, and context, all valid statements use the same `d`
tag. Relays following addressable-event semantics retain the event with the
greatest `created_at` value for that address.

A newer event can:

- replace trust with distrust;
- replace distrust with trust;
- cancel either value with `v = "0"`;
- update the human-readable reason without changing the trust value.

A statement in one context does not replace a statement in another context.

If two events have the same address and `created_at`, clients and relays SHOULD
retain the event with the lowest event ID in lexical order, as specified by
NIP-01.

## Time constraints

The optional `x` and `y` tags bound when a statement is active:

- `x` is inclusive activation time in Unix seconds.
- `y` is inclusive expiration time in Unix seconds.

If both are present, `x` MUST be less than or equal to `y`.

An event outside its active interval remains the newest event for its
addressable slot, but contributes no active trust edge. Clients MUST NOT fall
back to an older replaced event merely because the newest event is inactive or
expired.

## Validation checklist

A client accepting kind `32009` MUST verify:

1. the Nostr event signature;
2. exactly one `d` tag;
3. exactly one subject across `p`, `e`, and `i`;
4. exactly one `v` tag;
5. at most one `c`, one `x`, and one `y` tag;
6. subject syntax and normalization;
7. `v` is `1`, `0`, or `-1`;
8. time tags are base-10 Unix-second integers;
9. `x <= y` when both are present;
10. recalculated `d` equals the published `d`;
11. content does not exceed the implementation's accepted safety limit.

Unknown tags MAY be preserved and ignored.

## Querying

Clients can query statements by subject:

```json
{"kinds": [32009], "#p": ["<pubkey>"]}
```

or:

```json
{"kinds": [32009], "#e": ["<event-id>"]}
```

or:

```json
{"kinds": [32009], "#i": ["web:https://example.com/alice"]}
```

Clients can query an exact address when the author and `d` value are known:

```json
{
  "kinds": [32009],
  "authors": ["<statement-author-pubkey>"],
  "#d": ["<subject-id>:<context>"]
}
```

## Examples

The examples omit `id` and `sig` for readability.

### Trust a Nostr identity

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531200,
  "tags": [
    ["d", "<subject-pubkey>:development"],
    ["p", "<subject-pubkey>"],
    ["c", "development"],
    ["v", "1"]
  ],
  "content": "Maintains the library and consistently reviews security reports."
}
```

### Trust a Nostr event

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531250,
  "tags": [
    ["d", "<subject-event-id>:news:accuracy"],
    ["e", "<subject-event-id>"],
    ["c", "news:accuracy"],
    ["v", "1"]
  ],
  "content": "The primary sources support the claims in this event."
}
```

If the user selected a `note1` or `nevent1` reference, the publisher decodes it
and places the resulting 64-character event ID in both the `e` tag and the
subject portion of `d`.

### Distrust a web profile

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531300,
  "tags": [
    ["d", "<sha256-of-web-subject>:identity"],
    ["i", "web:https://x.com/example"],
    ["c", "identity"],
    ["v", "-1"]
  ],
  "content": "Impersonates another organization."
}
```

For AttentionX, X handles are lowercased and profile URLs omit a trailing
slash before hashing.

### Question an X post

The ternary values intentionally do not define a separate "question" state.
Applications that need a fact-checking workflow can express uncertainty in a
context rather than inventing another `v` value:

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531400,
  "tags": [
    ["d", "<sha256-of-web-subject>:news:accuracy"],
    ["i", "web:https://x.com/example/status/123"],
    ["c", "news:accuracy"],
    ["v", "-1"]
  ],
  "content": "The cited source does not support this claim."
}
```

User interfaces MAY display an unpublished local "question" state while
investigation is pending. A published kind `32009` statement remains strictly
ternary.

### Cancel a previous statement

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531500,
  "tags": [
    ["d", "<same-subject-id>:news:accuracy"],
    ["i", "web:https://x.com/example/status/123"],
    ["c", "news:accuracy"],
    ["v", "0"]
  ],
  "content": "The publisher issued a correction; withdrawing my statement."
}
```

### Time-bound trust

```json
{
  "kind": 32009,
  "pubkey": "<statement-author>",
  "created_at": 1672531600,
  "tags": [
    ["d", "<subject-pubkey>:access"],
    ["p", "<subject-pubkey>"],
    ["c", "access"],
    ["v", "1"],
    ["x", "1672531600"],
    ["y", "1672618000"]
  ],
  "content": "Temporary trust for this incident-response window."
}
```

## Client behavior

Clients SHOULD:

- choose their own trusted roots;
- ingest statements from explicitly selected authors or bounded graph paths;
- use positive `p` statements as traversal edges;
- treat `e` and `i` statements as terminal subjects rather than traversal
  edges;
- resolve one newest valid event per `(author, subject, context)`;
- enforce activation and expiration without reviving replaced events;
- cap path depth, fan-out, and processed event counts;
- show the context and source of trust information to users;
- distinguish direct statements from derived scores;
- retain enough provenance to explain a displayed result.

Clients MUST NOT present kind `32009` as a global or objective reputation
system.

## Security and privacy considerations

### Public statements

Trust and distrust are public signed claims. Users should understand that
publishing `-1` can have reputational and legal consequences.

### Subjective roots

Results depend on selected trust roots, contexts, path rules, and event
availability. Different clients can correctly produce different outputs.

### Sybil resistance

This event format does not itself prevent Sybil attacks. Clients should begin
from trusted roots and bound graph expansion.

### Context confusion

Trust in one context must not silently become trust in every context. User
interfaces should display context when it changes interpretation.

### Identifier ownership

A `web:` or `ext:` subject identifies a resource; it does not prove that a
Nostr key controls that resource. Ownership mappings require separate,
verifiable claims.

### URL instability

Web URLs can redirect, change ownership, or disappear. Applications may pair a
web subject with separately published content hashes or identity proofs when
long-term stability matters.

### Relay withholding

Relays may omit, delay, or selectively serve statements. Clients should use
multiple relays and avoid interpreting missing data as trust.

### Key compromise

A compromised author key can replace all statements made by that key. Clients
should support root rotation and should not cache derived scores indefinitely.

## Implementation rationale

Kind `32009` chooses one event per subject because independent addressable slots
are easier to reason about than batched trust events. Publishing more events is
an acceptable trade-off for deterministic replacement, cancellation, indexing,
and synchronization.

The ternary value is intentionally small. Rich labels, evidence, confidence,
and derived ranks belong in complementary events or application state rather
than changing the meaning of the graph edge.
